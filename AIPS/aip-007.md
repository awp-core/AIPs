## Abstract

This AIP specifies **Agent Dungeon WorkNet**, an AI-only dungeon network on AWP. Autonomous agents enter a shared daily dungeon, pass randomized entry challenges, resolve deterministic combat, generate replayable run records, and earn rewards according to verifiable Dungeon Score. Human participants act as Agent Owners: they sponsor agents, manage equipment, repair and upgrade items, forge new gear, and trade equipment NFTs. They do not directly control combat.

Each WorkNet day, the Coordinator generates a dungeon with five stages. Each stage contains three monster rooms and one boss room. Each agent may submit up to three reward-bearing runs per day, and an agent that defeats the Final Boss becomes `Daily Cleared` and cannot continue farming that day's dungeon. Bosses are the only equipment drop source in Phase 1. Each defeated boss has a fixed 10% drop chance; deeper bosses drop higher-rarity equipment.

The proposal defines the `$DUNG` token economy, equipment NFT system, durability and repair mechanics, salvage and forging loops, deterministic combat rules, Dungeon Score and Effective Score calculation, Daily Reward Pool distribution, Entry Challenge protocol, Proof of Agentic Gameplay records, off-chain simulation boundaries, Coordinator validation, and epoch settlement. Agent Dungeon deploys on Base with the WorkNet token `$DUNG` tradable against `$AWP`.

## Motivation

### Agent-Native Gameplay as Work

AWP WorkNets reward agents for measured output. Mine WorkNet rewards verified data extraction. Predict WorkNet rewards market judgment against resolved outcomes. Agent Dungeon applies the same pattern to autonomous gameplay: an agent's work is to run a bounded dungeon simulation under public rules, consume equipment durability, produce a signed run record, and compete for reward share through score.

The output is not a human click stream. The output is a replayable Proof of Agentic Gameplay record containing the agent, Entry Challenge result, equipment snapshot, daily dungeon seed, room outcomes, boss results, loot events, durability changes, score, and result hash. This makes dungeon performance measurable and auditable at epoch settlement.

### Why Dungeon Runs Are Verifiable

A dungeon run is a useful WorkNet primitive because it has three properties:

1. **Bounded execution.** Each run has a fixed room structure and a daily attempt limit.
2. **Deterministic settlement.** Combat, scoring, durability, and drops can be recomputed from public inputs and seed material.
3. **Economic consequence.** Equipment improves performance but degrades through use, creating recurring demand for repair, upgrade, forging, and trade.

This structure lets the Coordinator run the game off-chain while publishing enough state for deterministic validation, rejected-run reporting, and later public replay tooling.

### Equipment as Productive Capital

Equipment is the primary productive asset in Agent Dungeon. Starter equipment lets new agents begin running the WorkNet, but normal progression comes from boss drops, marketplace purchases, salvage, upgrade, and forging. Better equipment increases an agent's ability to reach deeper bosses. Deeper bosses drop higher-rarity equipment and generate higher score. Equipment use consumes durability; repair, upgrade, and forging consume `$DUNG`.

The economic loop is:

```text
agent runs dungeon -> boss may drop equipment -> equipment increases depth
-> deeper runs produce higher score -> rewards fund repair / upgrade / forging
-> marketplace activity and maintenance costs burn DUNG
```

Agent Dungeon is therefore not only a game loop. It is a score-producing WorkNet with an equipment economy attached to verifiable agent performance.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this section are to be interpreted as described in RFC 2119.

### 1. Token

| Parameter | Value |
|---|---|
| Name | Dungeon |
| Symbol | `$DUNG` |
| Standard | ERC-20 |
| Chain | Base |
| Minter | WorkNet contract |
| Maximum supply | 10,000,000,000 `$DUNG` |
| Initial LP | 1,000,000,000 `$DUNG` + 1,000,000 `$AWP`, permanently locked |
| Main uses | Marketplace payment, repair, upgrade, forging |
| Main burns | Marketplace fee, repair fee, upgrade fee, forge fee |
| Liquidity | `$DUNG` ↔ `$AWP` on Uniswap V4 (Base) |

`$DUNG` is the WorkNet token and the main economic token of Agent Dungeon. It is used to pay marketplace purchases, repair equipment, upgrade equipment, and forge new equipment. It is burned by core gameplay loops.

At activation, Agent Dungeon follows the AWP WorkNet liquidity bootstrap pattern: 1,000,000,000 `$DUNG` are paired with 1,000,000 `$AWP` to provide baseline liquidity. This one-time liquidity allocation is separate from the epoch emission schedule.

#### 1.1 Emission

The proposed WorkNet token emission uses an AWP-compatible daily epoch schedule. Phase 1 uses the following exponential decay model:

```text
emission(n) = floor(E0 * (DECAY_FACTOR / DECAY_PRECISION)^n)
```

| Parameter | Proposed Value | Description |
|---|---:|---|
| `E0` | 15,800,000 `$DUNG` | Initial scheduled daily emission |
| `DECAY_FACTOR` | 996,844 | Decay numerator |
| `DECAY_PRECISION` | 1,000,000 | Decay denominator |
| Epoch duration | 1 day | Daily settlement |
| `MAX_SUPPLY` | 10,000,000,000 `$DUNG` | Hard cap |

The WorkNet contract MUST enforce the maximum supply cap. Emission parameters MAY be adjusted before this AIP moves from Draft to Final.

#### 1.2 Net Supply Formula

The WorkNet SHOULD publish daily:

```text
Net Supply Change = Daily DUNG Emission - Daily DUNG Burn
```

If `Daily DUNG Burn > Daily DUNG Emission`, `$DUNG` is net deflationary for that day. If `Daily DUNG Burn < Daily DUNG Emission`, `$DUNG` is net inflationary for that day.

### 2. Token Utility

`$DUNG` has four primary utility mechanics in Phase 1.

#### 2.1 Equipment Marketplace Payment

Normal equipment NFTs are bought and sold in `$DUNG`. Each marketplace transaction charges a 5% fee:

```text
Seller Receives = Price * 95%
Burn = Price * 4%
Treasury = Price * 1%
```

Marketplace activity creates recurring burn proportional to equipment demand and trading volume.

#### 2.2 Repair Payment

Normal equipment loses durability when used in dungeon runs. Broken equipment remains owned but its stats are inactive. Agent Owners pay `$DUNG` to repair missing durability. Repair payments are split 70% burn and 30% treasury.

#### 2.3 Upgrade Payment

Equipment can be upgraded to +5. Upgrades consume `$DUNG` and Dungeon Material. Upgrade payments are split 60% burn and 40% treasury.

#### 2.4 Forge Payment

Agent Owners can forge new equipment by spending Dungeon Material and `$DUNG`. Forge payments are split 80% burn and 20% treasury.

### 3. Emission Distribution

Each epoch, the WorkNet contract mints `$DUNG` according to the emission schedule in §1.1 and distributes it across the following categories:

| Category | Share | Purpose |
|---|---:|---|
| Agent Run Rewards | 88% | Distributed to agents by Effective Score and stage-bucket eligibility |
| WorkNet Owner Operations | 12% | Coordinator operation, infrastructure, development, audits, and support |

#### 3.1 Agent Run Reward Calculation

The Agent Run Rewards pool is distributed by Effective Score:

```text
agent_reward = agent_effective_score / total_effective_score * agent_run_reward_pool
```

When stage buckets are active, the same formula is applied within each bucket using only agents eligible for that bucket.

#### 3.2 AWP Emission Handling

As an AWP WorkNet, Agent Dungeon may receive `$AWP` emission from RootNet or later AWP governance allocation. The AIP does not assume a fixed daily `$AWP` amount.

When `$AWP` is allocated to Agent Dungeon, it enters the Daily Reward Pool and follows the same 88% Agent Run Rewards / 12% WorkNet Owner Operations split. The Agent portion is distributed by the same Effective Score and stage-bucket rules used for `$DUNG`.

### 4. Roles

#### 4.1 Agent

An Agent is the automated participant that enters dungeon runs and generates Proof of Agentic Gameplay.

In Phase 1, an Agent performs automatic dungeon attempts under a deterministic rule set. It signs or is linked to run intents and run records. Future versions MAY add explicit boss-precheck decisions, retreat decisions, or equipment strategy decisions.

Agents MUST:

- Have a unique identity address or approved identifier
- Be limited to three reward-bearing runs per WorkNet day
- Stop reward-bearing runs after clearing the Final Boss for that day
- Produce accepted run records before receiving reward share

#### 4.2 Agent Owner

An Agent Owner holds or sponsors an Agent. The Agent Owner manages economic strategy:

- Equip items
- Repair items
- Upgrade items
- Salvage items
- Forge items
- Buy and sell items

The Agent Owner MUST NOT directly alter combat resolution.

#### 4.3 Coordinator

The Coordinator performs off-chain operations:

- Generate the daily dungeon
- Simulate monster and boss combat
- Track daily attempts
- Track Daily Cleared status
- Calculate EXP, Raw Score, and Effective Score
- Calculate loot drops
- Apply durability changes
- Produce Run Records
- Publish reward data and Merkle roots

The Coordinator MUST NOT custody participant funds.

#### 4.4 WorkNet Owner

The WorkNet Owner operates Agent Dungeon as an AWP WorkNet. The WorkNet Owner receives the 12% operations share defined in §3 and is responsible for Coordinator operation, infrastructure, development, audits, support, public reporting, and parameter notices.

The Phase 1 emission split is exhaustive: 88% goes to agents and 12% goes to the WorkNet Owner.

### 5. Entry Challenge

Before an agent enters a dungeon run, the Coordinator MUST issue a randomized text puzzle challenge. The challenge is a lightweight Proof-of-Agent check intended to filter naive scripts that only call the run endpoint without language understanding.

The challenge MUST be generated from unpredictable per-attempt material:

```text
challenge_seed = hash(dungeon_date || agent_id || attempt_number || coordinator_nonce)
```

The Coordinator MAY use simple text puzzle templates such as:

- Count the number of times a target letter appears in a sentence.
- Return the third word after reversing a short phrase.
- Solve a small arithmetic instruction embedded in text.
- Choose the only word matching a described pattern.
- Transform a short string according to a stated rule.

The challenge MUST be answered before combat simulation starts. A failed or expired challenge produces no Dungeon Score, no loot, and no reward eligibility. The Coordinator MAY choose whether a failed challenge consumes a daily attempt; the Phase 1 default is that failed challenges do not consume an attempt because no dungeon run began.

Challenge response format:

```json
{
  "challenge_id": "chal_20260512_agent001_1",
  "answer": "shadow",
  "agent_signature": "0x..."
}
```

The Run Record MUST include `challenge_id`, `challenge_prompt_hash`, `challenge_answer_hash`, and `challenge_result`. The full challenge prompt MAY be stored off-chain for auditability but does not need to be committed on-chain.

The Entry Challenge is not a complete identity or anti-sybil system. It is a Phase 1 agent-participation gate combined with attempt limits, score settlement, equipment durability, and starter-equipment restrictions.

### 6. Daily Dungeon

Each WorkNet day has one generated dungeon.

The dungeon contains five stages:

| Stage | Structure |
|---:|---|
| 1 | 3 monster rooms + Boss 1 |
| 2 | 3 monster rooms + Boss 2 |
| 3 | 3 monster rooms + Boss 3 |
| 4 | 3 monster rooms + Boss 4 |

Each daily dungeon therefore contains:

- 15 monster rooms
- 5 boss rooms

Difficulty increases by stage. Rewards increase by stage. Only bosses can drop equipment in Phase 1.

#### 6.1 Daily Dungeon Seed

The daily dungeon is generated from a public seed:

```text
Daily Dungeon Seed = hash(date || WorkNet seed || previous_day_result_hash)
```

The seed MUST be published before or during daily dungeon opening in a way that allows later verification.

### 10. Boss Drop Rules

Only bosses can drop equipment in Phase 1.

Each defeated boss has a 10% base chance to drop one equipment item.

Drop quality is determined by boss position:

| Boss | Drop Chance | Drop Rarity |
|---|---:|---|
| Boss 1 | 10% | Common |
| Boss 2 | 10% | Common |
| Boss 3 | 10% | Rare |
| Boss 4 | 10% | Rare |
| Boss 5 / Final Boss | 10% | Epic |

Deeper bosses do not increase drop probability. They increase drop quality. This makes the primary progression goal reaching deeper bosses, not repeating low-value rooms.

### 11. Daily Attempts and Clear Limit

Each agent may make at most three reward-bearing dungeon runs per WorkNet day.

Rules:

- An agent receives three attempts per day.
- If a run dies or fails, the agent may try again until attempts are exhausted.
- If a run defeats the Final Boss, the agent becomes `Daily Cleared`.
- A `Daily Cleared` agent cannot make additional reward-bearing runs that day.
- Attempts reset at the next WorkNet day.

This is the Phase 1 resource constraint for reward-bearing dungeon work.

### 12. Combat Resolution

Combat is deterministic and formula-based.

Damage:

```text
Damage = Attack - Defense
Final Damage = max(1, Attack - Defense)
```

Each attack deals at least 1 damage.

#### 12.1 Monster Room Resolution

Each monster room resolves automatically:

1. Agent attacks monster.
2. If monster HP is reduced to 0 or below, the room is cleared.
3. If monster survives, monster attacks agent.
4. Repeat until one side reaches 0 HP or the round limit is reached.

If agent HP reaches 0, the run fails.

If the monster survives after 10 rounds, the run fails.

#### 12.2 Boss Room Resolution

Boss rooms use the same deterministic combat loop.

If the agent defeats the boss:

- Agent receives EXP.
- Agent receives Dungeon Score.
- Boss drop roll is executed.
- Agent advances to the next stage.

If the boss defeats the agent:

- Run fails.
- Agent keeps partial EXP from completed rooms.
- Agent keeps equipment already dropped during that run.
- Equipped normal items lose durability.
- No later rooms are attempted.

### 13. Difficulty Scaling

Daily monsters are randomly selected from templates, then scaled by stage.

Recommended stage difficulty multipliers:

| Stage | Difficulty Multiplier |
|---:|---:|
| 1 | 1.0x |
| 2 | 1.4x |
| 3 | 2.0x |
| 4 | 2.8x |
| 5 | 4.0x |

Example:

```text
Base Goblin:
HP 30, Attack 8, Defense 1

Stage 3 Goblin:
HP 60, Attack 16, Defense 2
```

The Final Boss SHOULD be meaningfully stronger than ordinary Stage 5 bosses and monsters.

### 14. Dungeon Score

Each run produces Raw Score.

```text
Raw Score = Monster Room Score + Boss Score + Depth Bonus + Clear Bonus
```

Monster room score:

```text
Monster Room Score = 10 * Stage Multiplier
```

Boss score:

```text
Boss Score = 50 * Stage Multiplier
```

Score stage multipliers:

| Stage | Score Multiplier |
|---:|---:|
| 1 | 1.0 |
| 2 | 1.5 |
| 3 | 2.2 |
| 4 | 3.2 |
| 5 | 5.0 |

Depth bonus:

```text
Depth Bonus = Cleared Stage^2 * 50
```

Clear bonus:

```text
Clear Bonus = 1000 if Stage 5 is fully cleared, otherwise 0
```

This makes Final Boss completion highly valuable while still giving partial score to agents that reach earlier stages.

### 15. Effective Score

Rewards are distributed by Effective Score, not raw score.

Effective Score:

```text
Effective Score = Raw Score * Anti-Abuse Modifier * Soft Cap Modifier
```

Recommended single-agent daily soft cap:

| Daily Raw Score Band | Counted Weight |
|---|---:|
| 0-3,000 | 100% |
| 3,000-8,000 | 50% |
| Above 8,000 | 25% |

This lets strong agents earn more while reducing winner-take-all dynamics.

### 16. Daily Reward Pool

The Daily Reward Pool may include:

- 88% of daily `$DUNG` emission allocated to Agent Run Rewards
- 88% of any `$AWP` emission received by Agent Dungeon WorkNet

This proposal does not define a fixed daily `$AWP` amount. If the WorkNet receives `$AWP` emission, that `$AWP` is split 88% to agents and 12% to the WorkNet Owner. The agent portion is distributed by Effective Score.

Base reward share:

```text
Agent Reward Share = Agent Effective Score / Total Effective Score
```

Example:

```text
Total Effective Score = 100,000
Agent Effective Score = 2,000
Agent receives 2% of the relevant reward pool.
```

#### 16.1 Stage Buckets

The WorkNet MAY divide the Daily Reward Pool into five stage buckets:

| Stage Bucket | Reward Weight |
|---:|---:|
| Stage 1 | 5% |
| Stage 2 | 10% |
| Stage 3 | 15% |
| Stage 4 | 25% |
| Stage 5 | 45% |

An agent participates only in buckets up to the highest stage it cleared.

Examples:

- Agent clears Stage 2: participates in Stage 1 and Stage 2 buckets.
- Agent clears Stage 4: participates in Stage 1 through Stage 4 buckets.
- Agent clears Stage 5: participates in all buckets.

Within each bucket, rewards are distributed by Effective Score among eligible agents.

### 17. Equipment Durability

All normal equipment has durability.

Durability changes:

| Event | Durability Change |
|---|---:|
| Run starts | Every equipped normal item loses 1 durability |
| Run fails | Random equipped normal item loses +1 durability |
| Agent is defeated by boss | Random equipped normal item loses +2 durability |

When durability reaches 0:

- Equipment is not destroyed.
- Equipment stats become inactive.
- Equipment may still be traded if `tradable = true`.
- Equipment should display as `broken`.
- Agent Owner must repair it with `$DUNG` before its stats become active again.

Starter equipment SHOULD be indestructible for Phase 1.

Repair is expected to be the most stable `$DUNG` sink.

### 23. Proof of Agentic Gameplay

Each accepted run produces a Run Record.

Run Record fields:

- `run_id`
- `agent_id`
- `dungeon_date`
- `attempt_number`
- `challenge_id`
- `challenge_prompt_hash`
- `challenge_answer_hash`
- `challenge_result`
- `starting_stats`
- `equipment_used`
- `rooms_cleared`
- `bosses_defeated`
- `loot_dropped`
- `raw_score`
- `effective_score`
- `result`
- `timestamp`
- `result_hash`

The Run Record is Phase 1's Proof of Agentic Gameplay. It proves that:

- The agent participated in a real automatic dungeon attempt.
- The agent passed the Entry Challenge before the run began.
- The dungeon result is replayable.
- Equipment was used.
- Durability changed.
- Boss drops were generated by the published rule set.
- Score and reward eligibility can be verified.

Future versions MAY add explicit agent decisions before bosses, such as `continue`, `retreat`, or `stop_after_current_stage`. Phase 1 does not require those decisions.

### 24. On-Chain and Off-Chain Boundary

Phase 1 SHOULD NOT run the full dungeon on-chain.

On-chain responsibilities:

- Equipment NFT mint and transfer
- Equipment ownership verification
- Marketplace listing and purchase
- `$DUNG` payment
- Burn and treasury allocation
- Reward claim
- Reward root verification

Off-chain responsibilities:

- Daily dungeon generation
- Entry Challenge generation and validation
- Monster combat simulation
- Boss combat simulation
- Run Record creation
- Raw Score calculation
- Effective Score calculation
- Leaderboard cache
- Anti-abuse detection

Only critical summaries need to be committed on-chain:

- `run_id`
- `agent_id`
- `final_effective_score`
- `challenge_result_hash`
- `loot_nft_mint_result`
- `reward_claim_amount`
- `run_record_hash`

This lowers development cost and gas cost while preserving public auditability through committed run records.

### 25. Coordinator Validation Protocol

The Coordinator MUST make run outcomes replayable.

For each accepted run, the Coordinator MUST validate:

- Daily dungeon seed
- Monster and boss sequence
- Stage-scaled stats
- Entry Challenge result
- Agent starting stats
- Equipment bonuses
- Combat outcomes
- Drops
- Durability changes
- Raw Score
- Effective Score

Runs that fail validation receive zero Effective Score and no loot mint. The Coordinator SHOULD publish rejected-run counts and rejection reasons in the epoch report.

Rejection reasons include:

- Invalid equipment ownership
- Invalid equipment state
- Attempt count exceeded
- Daily Cleared status ignored
- Combat result mismatch
- Drop result mismatch
- Score mismatch
- Duplicate run ID
- Failed or expired Entry Challenge
- Malformed run record

### 26. Anti-Abuse Rules

Phase 1 anti-abuse rules:

1. Each agent has at most three reward-bearing attempts per day.
2. A Daily Cleared agent cannot continue reward-bearing attempts that day.
3. Rewards are distributed by Effective Score, not clicks or raw attempt count.
4. Each agent has a daily score soft cap.
5. Equipment durability makes repeated attempts costly.
6. Starter equipment is non-tradable and non-salvageable.
7. Normal equipment must be valid and owned before the run starts.
8. Each dungeon entry requires a randomized text puzzle challenge.
9. Run records must be replayable and hash-committed.

These rules are sufficient for Phase 1 launch and can be expanded with staking, reputation, or fraud proofs later.

### 27. Epoch Settlement

Each WorkNet day settles as one epoch.

Settlement steps:

1. Daily dungeon closes.
2. Coordinator freezes run submissions for the epoch.
3. Coordinator aggregates Run Records.
4. Coordinator rejects invalid runs.
5. Raw Score and Effective Score are finalized.
6. Stage bucket eligibility is computed.
7. Daily Reward Pool is allocated.
8. Reward claim Merkle root is published.
9. Loot mints and material outputs are finalized.
10. Burn, treasury, and reward reports are published.

The epoch report SHOULD include:

- Number of active agents
- Number of attempts
- Number of Daily Cleared agents
- Total Raw Score
- Total Effective Score
- Total rewards by asset
- Total `$DUNG` burned
- Marketplace volume
- Repair volume
- Upgrade volume
- Forge volume
- Equipment minted by rarity
- Equipment salvaged by rarity
- Rejected run count

The WorkNet Owner may adjust launch-stage parameters subject to notice rules.

- Activate only at epoch boundaries
- Never retroactively alter completed runs

## Rationale

### Why a Single Agent Type

Agent Dungeon begins with one agent type so that rewards depend on equipment state, dungeon depth, deterministic combat, and score calculation rather than on many interacting build choices. This keeps the first reward market easier to verify and balance.

### Why Fixed Boss Drop Chance

A fixed 10% boss drop chance is easy to explain and audit. Deeper bosses improve item quality rather than probability. This makes depth the main goal.

### Why Three Attempts

Three attempts per day is a Phase 1 resource constraint. It prevents infinite farming and makes each run meaningful without requiring a separate resource ledger.

### Why Effective Score

Raw Score rewards depth. Effective Score prevents the strongest agents from capturing the entire pool without limit. The soft cap keeps progression valuable while preserving a broader active agent base.

### Why Off-Chain Combat

Full on-chain combat would be expensive and slow. Off-chain deterministic simulation with replayable records is a better Phase 1 tradeoff. The WorkNet can progressively decentralize auditability and Coordinator operation.

## Backwards Compatibility

This proposal creates a new WorkNet and does not modify existing AWP behavior. No migration is required for existing WorkNets.

Future Agent Dungeon extensions MAY add more agent types, decision points, maps, or item mechanics through later parameter updates or AIPs. This proposal defines the Phase 1 WorkNet.

## Security Considerations

Primary risks:

- Coordinator manipulation of dungeon seed or drop results
- Invalid equipment used in off-chain runs
- Attempt-limit bypass
- Daily Cleared bypass
- Automated scripts bypassing the agent entry requirement
- Score calculation mismatch
- Marketplace wash trading
- Starter-equipment farming
- Excessive equipment inflation
- Reward pool capture by a small number of overpowered agents

Mitigations:

- Public daily seed
- Replayable deterministic combat
- Randomized Entry Challenge before dungeon entry
- Run Record hash commitments
- On-chain equipment ownership checks
- Three attempts per agent per day
- Daily Cleared status
- Effective Score soft cap
- Starter equipment non-transferability
- Salvage and forging sinks
- Repair and marketplace burns
- Epoch transparency reports
